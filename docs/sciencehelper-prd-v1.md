## 1. 产品定位和边界

面向科研人员的“课题 → 可追溯文献/Methods → 可购试剂 → 微信支付 → 商家发货”工作台。科研人员可直接发布课题，或先从 5 篇 PubMed/Europe PMC 文献生成研究方案，再选择方法和试剂。商家用自己的账户上架商品并处理其订单。

当前实现是单体 Node/React + JSON 数据存储；不是托管资金平台，也不应把样例 SKU、模拟实验室、算法建议宣传成经核验的真实供给或科学结论。20,000 条文献标题课题目录在仓库中，**尚未接入站内任务广场自动发布**。公开任务只是课题描述，不包含研究方案原文、收货地址、账号信息。

### 目标与衡量

| 目标 | 指标及口径 | 验收目标（拟定，待业务确认） |
| --- | --- | --- |
| 研究激活 | 注册用户 7 日内至少创建 1 个方案或任务 / 新注册用户 | ≥30% |
| 研究到采购 | 任务用户 14 日内加入至少 1 个真实可售商品 / 任务用户 | ≥10% |
| 支付可靠性 | 微信成功支付通知或查询最终入账且仅扣库存一次 / 成功支付笔数 | 100% |
| 履约及时性 | 已付款订单 48 小时内填写有效物流单号 / 已付款订单 | ≥90%（商家协议落地后） |
| 隐私 | 未主动选择公开的任务被他人读取次数 | 0 |

这些是建议目标，不是已测得的线上指标；埋点与基线均待建立。首版不包含自动结算佣金、退款/售后自动化、商家资质审核、跨商家分账、电子合同或临床诊疗建议。

## 2. 角色、权限与数据

| 角色 | 可操作 | 不可操作 |
| --- | --- | --- |
| 游客 | 查看登录/注册页 | 任务、订单、购物车与管理接口 |
| 注册科研用户 | 创建自己的方案/任务，选择可售商品，支付并查看自己的订单 | 修改其他用户任务/订单或其他商家的商品/运单 |
| 商品归属商家 | 发布和维护自己商品，查看对应订单在收款后的收件信息，录入运单 | 他人商品、未付款订单发货、查看无关订单 |
| 平台运营 | 拟规划角色与权限 | 当前 `marketAdmin`/`modelAdmin` 仅为独立 UI 壳层，**尚无正式管理员授权模型**；不能当作已隔离的生产后台 |

核心键：`user.id`、`project.id/createdBy`、`task.id/userId/projectId/visibility`、`reagent.id/ownerUserId`、`order.id/userId/taskId/outTradeNo`、`fulfillment.merchantId`、`transactionId`。文献 `PMID/PMCID/DOI`、Methods 节点 `paperIds` 为证据追溯；模型版本、参数快照、分析运行 ID 尚待补充。

## 3. 页面级需求

### 3.1 注册登录与科研方案（`/#research`）

入口为网站首页。邮箱、密码登录；注册姓名至少 2 字、邮箱格式有效、密码至少 8 位。未登录访问 API 返回 401。课题文本最少 4 字、最多 1200 字；先禁用重复提交，检索 Europe PMC/NCBI 后记录 5 篇文献、出处、摘要/全文证据范围、方法树和创建者。网络失败保留用户输入并可重试；推理降级时显示证据范围，不将模型生成内容描述为实验结论。

| 编号 | 行为与状态 | 验收 |
| --- | --- | --- |
| SH-RS-001 | 用户输入课题并生成方案；运行中显示检索/解析阶段，可停止。 | Given 有效课题，When 提交，Then 仅自己的方案可见，5 篇结果均有 PubMed 来源；失败保留输入。 |
| SH-RS-002 | 用户在方法树勾选有目录匹配的试剂，加入本人购物车。 | 未匹配/无商家归属的试剂不能误标“可购买”；加入数量不得超库存。 |

### 3.2 任务发布与可见性

入口为研究工作台的“直接发布科研任务”或已有方案的“发布科研任务”。直接发布只需课题文本；关联方案发布应自动带入课题。任务默认 `private`，用户勾选或事后切换 `public` 后才在“平台最新科研任务”显示标题与日期；其他用户不能读取私密任务或修改任意他人任务。公开前应明确提示不得提交个人信息、未公开研究资料和患者隐私。未来引入审核、举报和撤回状态；本期只有可见性切换，没有内容审核，不应做大规模公共推广。

| 编号 | 字段/行为 | 校验与验收 |
| --- | --- | --- |
| SH-TK-001 | `topic` 文本，必填；方案发布可自动填入。 | 4–1200 字，空或不足返回 400；提交成功生成 `task.id`。 |
| SH-TK-002 | `visibility`：`private`/`public`，默认 `private`。 | Given 私密任务，When 他人读取广场，Then 不出现；只有本人能 PATCH 切换。 |
| SH-TK-003 | 重复关联同一方案发布。 | 返回原有任务，不产生重复条目。 |

### 3.3 试剂商城与购物车（`/#market`）

商品需有归属商家、在售状态、正价格和可售库存。未绑定商家的历史样例商品仅展示“暂不可购买”；不同用户购物车相互隔离。商城“当前研究方案”应取实际用户方案匹配结果，不放固定演示课题。型号/库存/价格以商家当前数据为准，文献推荐和真实库存是不同证据源。

| 编号 | 行为 | 异常与验收 |
| --- | --- | --- |
| SH-MK-001 | 商家发布商品：名称、价格、库存必填；价格精确到分、库存非负整数。 | 非法字段返回 400；创建后 `ownerUserId` 为当前用户。 |
| SH-MK-002 | 商家修改或下架自己的商品。 | 他人修改返回 403；已有订单商品禁止物理删除，需下架。 |
| SH-MK-003 | 用户加入、调整、删除购物车商品。 | 无商家/已下架/超库存返回明确原因；购物车仅本人可见。 |

### 3.4 结算与微信 Native（确认订单弹窗、`/#orders`）

字段：收件人 1–80 字、国内 11 位手机号、完整地址 6–400 字，均必填；任务关联可选且只能选择本人任务。服务端以购物车商品重新计价，微信 V2 统一下单生成订单专属二维码，过期时间按北京时间格式传递，前端使用服务端生成的二维码图像。查询与异步通知必须验证签名、APPID、商户号、订单号、金额和交易号。用户点击“查询支付状态”只是核验，不可自行标记已付款；仅微信成功结果推进到“待商家确认”。重复待支付订单阻断，用户回购买记录继续支付；二维码约 2 小时到期后仍应允许查询迟到付款。库存只在第一次成功确认时扣减一次。

| 编号 | 行为 | 异常与验收 |
| --- | --- | --- |
| SH-PY-001 | 提交订单前校验地址、价格、在售商家和库存。 | 缺项、变价、无商家或超库存不产生本地订单；下单等待时按钮禁用。 |
| SH-PY-002 | Native 预下单成功显示站内二维码。 | 真实商户可返回 `weixin://`；第三方二维码图片站点不可用不影响显示。 |
| SH-PY-003 | 微信回调/查询确认付款。 | 伪造签名/错误金额/错误订单不入账；重复回调与查询不重复扣库存。 |
| SH-PY-004 | 查询超时或二维码过期。 | 保留订单和可恢复的提示，未核验前不能发货；用户不能手工确认付款。 |

支付状态 `pending → paid` 或 `pending → expired`；过期仍可因微信最终成功结果转 `paid`。订单履约状态 `待支付 → 待商家确认 → 部分发货/已发货`。退款与关闭订单属于后续版本，须先设计支付关闭/退款与库存返还的一致性。

### 3.5 商家履约（`/#merchant`）与买家记录（`/#orders`）

商家只看到自己商品所对应的履约组，收件信息仅在确认付款后可见；物流公司必填，运单号限 5–80 位字母、数字和连字符。未付款、非归属商家和重复发货均拒绝。多商家订单各自录入运单，全部发货才变为“已发货”；买家查看商品快照、任务关联、支付与物流状态。

| 编号 | 行为 | 验收 |
| --- | --- | --- |
| SH-FL-001 | 已付款商家填写物流公司和运单号。 | Given `paid` 且商家匹配，When PATCH 发货，Then 买家能看到运单；重复发货 409。 |
| SH-FL-002 | 无关商家或未付款发货。 | 分别返回 404/409，收件地址不泄漏给无关用户。 |
| SH-FL-003 | 多商家订单。 | 每个商家只能变更自己的履约组，部分/全部发货状态聚合正确；尚需增加自动化回归。 |

## 4. 非功能与上线门槛

- 单实例 JSON 持久化目前采用临时文件替换，不能作为高并发交易数据库。放量前迁移事务数据库并加订单唯一键、支付事件幂等表、库存预留、审计日志与备份演练。
- 密钥仅在服务器 `.env`；不进入仓库或浏览器。日志不得打印私钥、完整手机号/地址、二维码载荷。支付回调应限制请求体大小、检查 HTTPS 通知域名与微信商户配置。
- 页面需要桌面/移动端可用、键盘可操作，错误信息能保留输入并提供重试。二维码弹窗关闭后可在购买记录恢复。
- 商品真实性、商家资质、发票、退货、客服 SLA 和支付主体须经业务/法务确认；未确认前不能宣称“官方旗舰店”“严选认证”“快速配送”等履约保障。
- 科研建议属于候选方案，必须展示文献证据和原文复核提示，不作诊疗或临床决策用途。

## 5. 测试与待确认

当前自动化 `node --test tests/order-flow.cjs` 通过模拟微信验签/查询，覆盖注册、方案、任务、跨用户隔离、上架、购物车、下单、伪造通知拒绝、支付确认、扣库存、发货与物流可见。阿里云真实商户完成过未付款 0.01 元预下单验证。**真实扫码扣款、回调、退款与商家实际交接仍未验收**，需由商户负责人安排小额真实交易并对账；不得把预下单验证视作完整资金闭环。

| 待确认项 | 负责人建议 | 放行条件 |
| --- | --- | --- |
| 商家准入、SKU 权属与供货协议 | 商家运营/法务 | 首批可售 SKU 有真实商家负责履约 |
| 支付、退款、发票、佣金与资金结算主体 | 财务/法务/商户管理员 | 书面流程及真实小额支付/退款验收 |
| 任务广场公开内容审核与举报机制 | 科研负责人/安全运营 | 扩大公开入口推广前完成 |
| 数据库迁移、备份与故障恢复 | 后端/运维 | 超过小规模试点前演练通过 |
